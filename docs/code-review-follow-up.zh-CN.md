## 2. 本轮已约定实施范围

**不改数据库 schema：保持 schema 10、37 张注册表及现有相册格式边界。** 不新增 revision/current-pointer 表，不实现旧库转换或隐式迁移，不修改用户旧相册或备份。仍只有 ingestion / index / management 三个公共能力；查询默认、授权范围、只读查询和静态文件夹语义不因本次审查自动改变。

## 3. 延期：R2 append-only 结果版本与历史读取

**状态：未批准，短期 `vector_hash` 补丁不解决本节。**

- **审查事实：**相同 embedding 输入键修复会保留 `result_id` 并替换向量。单条件旧快照原先只认 ID，可能继续显示旧分数；scene 历史依赖保存了旧 `vector_hash`，读取时却检查同一 ID 下的新向量，因而可能报 `FEATURE_RESULT_INVALID`。这是“历史 payload 可读性”和“当前依赖有效性”耦合的问题，不只是向量是否合法。
- **重新讨论触发条件：**需要修复后的结果历史仍可审计、跨备份读取 scene 历史，或开始设计 R4 的合法修复流程。即使新向量合法、甚至与修复前数值一致，也必须定义结果版本与 provenance 语义。
- **可选方案（均未批准）：**①追加 revision/result ID，独立选择 current；②保留当前存储边界，先设计历史 payload 与依赖完整性状态分离的读取协议；③统一 embedding、feature 与 prototype 的 revision 模型。后两者也不能把无法验证的来源标为正常 current。
- **待决策：**历史是否允许“可读但来源损坏”；旧 ID 指向什么；有效旧版本如何保留；缺失/损坏依赖如何逐条报告；current 选择、失效传播、快照兼容和保留策略是什么；是否需要新 schema 与显式另存转换。
- **候选验收标准：**相同/不同合法向量修复均有明确身份；旧单条件快照 show/add 拒绝不匹配来源；scene 历史 payload 可读取或得到逐项诊断，不因一项损坏阻断整页；current 准确失效；跨备份行为可复现；不丢旧结果、不扩大计算授权。
- **依赖：**先完成 R2 哈希校验止损；与 R4、prototype 历史、快照协议共同设计。任何 schema 变更、旧库转换与保留政策需独立批准，不在本轮实施。

## 4. 延期：R4 损坏 feature/prototype 的显式修复

**状态：未批准，不将“已检测损坏”写成“已具备修复”。**

- **审查事实：**`invalid_result` 被计划为 skip，执行状态还可能落为 `invalid_input`；same photo/profile/fingerprint 的唯一约束及不可更新/删除 evidence 规则阻止直接写替代结果。损坏 typed detail 后重复导入相同文件通常不产生新输入版本，无法自然修复。只把 action 改为 compute 会撞上旧记录，并不是完整方案。
- **重新讨论触发条件：**真实出现需要恢复的损坏结果、prototype 或依赖；需要把 coverage 诊断接到用户可执行的受控恢复流程。
- **可选方案（均未批准）：**①显式 repair plan 追加 revision 并隔离旧损坏版本；②在拥有有效备份时设计另存恢复/校验流程；③先仅改进逐条损坏诊断及历史读取，不开放写修复。不要用随意更改参数/profile 来冒充相同计算的修复。
- **待决策：**输入损坏、结果损坏、依赖损坏如何区分；允许修复哪些证据；如何确认精确输入和计算范围；唯一约束/current 选择如何变化；prototype 如何恢复；损坏版本保留、隔离和审计规则；缺原图/模型时是否只能诊断。
- **候选验收标准：**覆盖 typed detail、payload hash、prototype 和依赖损坏；新修复版本可验证，旧记录可诊断，下游 current/stale 准确；计划/执行失败可回滚；已批准 reuse 失效不能静默升级为 compute；未获批准不读原图、不调用模型、不删除旧证据。
- **依赖：**先决定 R2 历史/版本模型和新 schema/转换策略；复用正确的 profile/provider 校验、输入验证、执行锁及短事务。诊断改进也须另行明确范围，不借本轮恢复名义修改数据库合同。

## 5. 延期：R6 显式、可证明所有权的模型缓存恢复

**状态：未批准；本轮 R5 只解决活锁/崩溃锁，不修复已发布资产。**

- **审查事实：**feature 资产目录已存在时，setup 只做验证；缺文件、错误内容或 OWNER 损坏会失败，不进入下载/重发布。探针使用虚拟资产，下载调用为零，没有测真实网络恢复。普通执行保持离线失败，不会自动补下载。
- **重新讨论触发条件：**程序拥有的已发布缓存缺失/损坏，或需要验证下载中断/发布失败后的恢复。不能把第三方、用户自有或所有权不明的目录自动视为可清理缓存。
- **可选方案（均未批准）：**①generation + staging + current-pointer，新 generation 验证后发布，保留旧可用 generation；②显式授权在新的受控缓存根重新 setup，再由用户选择该根；③为可证明 owned 的缓存设计受控隔离/重建。OWNER 损坏时必须单独定义可接受的所有权证明，不能把损坏标记本身当作所有权。
- **待决策：**恢复命令/确认交互、目录所有权与边界、校验后复用或重取哪些文件、下载许可/磁盘预算、失败时保留什么、何时切换 current、清理权限与中断续传策略。不得据提案增加自动删目录或普通执行下载。
- **候选验收标准：**缺一文件、同尺寸错误内容、OWNER 损坏、下载中断、发布失败、活跃读者/竞争 setup、未知目录与路径别名；失败不破坏旧可用 generation 或非 owned 文件；有效资产才可发布；资源不足返回清楚诊断；无下载批准时不联网。
- **依赖：**R5 OS 锁、资产 manifest/checksum、所有权协议和安全发布策略；复用 R1 的发布原则但须独立验证目录/平台语义。不要求改变相册 schema，也不能因此跳过用户对恢复方案的决策。

## 7. 后续决策顺序与完成条件

1. 先验证本轮已约定修复，按项记录实际运行的 targeted tests、跳过原因和未测边界；不把本文件的验收目标充作通过记录。
2. 将 R2 历史版本与 R4 损坏证据修复共同形成独立设计；若涉及 schema/旧库转换，单独批准再实现。
3. R6 可以独立设计，但必须先明确 owned cache、下载许可和安全发布/失败保留策略，不能以“锁已恢复”推断资产也能恢复。
4. 产品语义、排序、架构与其他优化/质量议题分别选定目标与预算；没有证据和决策就保持现行能力，不把审查建议全部排成已批准的路线图。
5. 每项延期工作获批时，应补齐责任范围、选定方案及否决理由、数据/权限/schema 影响、依赖、可执行验收与回退方式，然后再更新运行文档。运行 Skill 不依赖本讨论文档。
