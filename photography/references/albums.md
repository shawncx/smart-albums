# Albums are files; virtual folders are static collections

Start with [selecting or creating a SQLite album file](library.md). This reference
describes file lifecycle and its distinction from virtual folders, not the removed
multiple-albums-per-database interface. There are exactly three Skill capabilities;
file lifecycle and folder management both belong to management.

Prefix examples with:

```text
python <skill-directory>\scripts\photography.py --database <absolute-album.sqlite>
```

Then use:

```text
management create
management open
management photos --limit 100
management photo <photo-id> --html <output-directory>\photo.html
management backup --output <new-backup.sqlite>
```

- **Create:** explicit new-file permission, unused path, no overwrite.
- **Open:** read-only format/identity/coverage inspection; no DDL, repair or migration.
- **Browse:** saved photos/previews without model installation or original-file access.
- **Backup:** consistent SQLite snapshot at a new destination; originals and models
  are not included.

The response's album UUID survives moving/renaming; the display name is the current
filename without extension. The database path selects the album, not an internal
ID. Switching files requires clearing the previous photo/profile/run/folder context and
pending confirmations. A copy/backup retains the UUID and is not a new independent
album to edit concurrently.

Ingestion can add photos from several folders to the same file. Source roots are
saved scan information, not libraries to select or membership collections. There
is no `--album-name`, `--album-id`, `--library-id`, internal album membership operation or
retained legacy multi-album command/selection protocol. Search covers only the selected file.

## Virtual folders inside the album

Manual custom folder CRUD/add/remove is primary and requires no index. Folders are
static, flat many-to-many collections, not disk directories, internal albums or a
fourth capability. `management folders` supports empty custom folders and stable
IDs; names are unique by trimmed NFC + casefold. A single-photo add uses a
one-element JSON ID array generated by the Skill. Removing membership/deleting a
folder never deletes photos, originals, thumbnails or embeddings or other memberships.

`photos` and all search modes accept repeatable `--folder-id`; multiple distinct
IDs require `--folder-match union|intersection`. No IDs means the whole album;
invalid folders error and empty scopes stay empty. Optional confirmed date plans
and selected-search additions are one-time conveniences, not automatic regrouping
or live rules. All memberships travel inside SQLite backups/moves.

New albums use schema 10 with 37 registered tables (32 ordinary, one external-content
FTS5 virtual table and four explicitly registered shadows; excluding internal `sqlite_sequence`), including
`virtual_folders(folder_id, name, name_key, description, created_at, updated_at)` and
`virtual_folder_photos(folder_id, photo_id, added_at)`. Management reports use
`album-snapshot-v2` with historical album/folder scope. Old v1–v9 databases are rejected unchanged,
not migrated, emptied or overwritten. Cross-file search, merging albums, shared
photo/vector records and automated cloud synchronization are outside this version.

See [management](management.md) for original-path maintenance and exports,
[ingestion](ingest.md) for stable path identity, and [index](index.md) for confirmed
embedding and six opt-in feature components. Their profiles/results, dependencies,
scene text prototypes and OCR derivative travel with backups; weights do not.
Stage 2 OR search is implemented through separate legacy [condition commands](search.md#stage-2-or-condition-workflow); targeted integration checks have passed. Explicit legacy metadata/semantic behavior is unchanged. New natural-content requests use [default unified search](search.md#unified-query-json), whose query-file variant keeps folder scope in the file. It saves private evidence and returns numbered candidates with `review_id`, defaulting to 100 globally deduplicated candidates or an explicitly requested positive count/`all`. Querying remains read-only. Only explicit `folders add --review-snapshot` with the matching review ID and a previously selected numbered subset writes unified-result memberships. Legacy `--search-snapshot`/`--query-snapshot` keep photo IDs; all three flags are mutually exclusive, never live rules.
Stop all writers before moving/syncing files; a portable database
does not imply that originals or a compatible runtime are available on another host.
